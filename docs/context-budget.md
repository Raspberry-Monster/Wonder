# 统一上下文与 Token 预算

所有模型调用通过 `ModelRouter.Context` 创建当前模型的 `ModelContextBudget`，通过 `TokenCounter` 使用已发现的词表或估算器计数。组件之间传递同一个请求的预算对象；不同模型仍各自使用对应词表、窗口和输出设置。最终检查返回的输入计数同时用于额度预留和日志，避免重复分词。它不是跨用户共享的可变余额，也没有新增全局锁。

## 一次请求如何装入上下文

可用输入 = ContextWindow − 输出预留 − 512 Token 余量。计数包含实际格式化后的消息、工具定义、工具调用和结果，以及图片的估算开销。最终发送前，ModelRouter 再检查完整请求。

私聊必须保留系统指令、本轮情绪与时间资料和当前消息。先构造完整候选请求，再按优先级移除可选内容：较早历史、记忆、关系、最近历史、摘要；历史按完整轮次移除，历史工具调用及其结果始终属于同一组。工具模式继续预留 ToolReserve。数据库 User／Assistant 历史上限为 40 条，动态资料及 Tool 消息不计入该上限。必要内容本身超限时明确失败，不截断当前问题。

历史工具按照剩余 Token 筛选记录、缩短摘录。同一轮多个工具结果共用预算，前一个结果会占用后一个结果的空间。必要的工具链增长时，可降低下一次生成的输出上限；仍保留至少配置输出与 256 Token 中的较小值。确实没有空间时返回简短错误或停止，无法保证任意长工具链都能继续。

## 私聊 Context 缓存与原样重放

| 顺序 | 修改前 | 修改后 |
| :---: | --- | --- |
| ① | System：Shared、身份、情绪、时间 | 稳定 System：Shared、身份、ChatContext 解释规则及工具可用状态 |
| ② | 滚动摘要 | 基础上下文：有效摘要及兼容旧历史 |
| ③ | 本轮关系、检索记忆 | 已发送的历史请求和最终回复，保持实际协议角色、内容及工具链 |
| ④ | 每轮重新包装历史消息 | 本轮动态资料：情绪、应用时间、关系、检索记忆 |
| ⑤ | 当前用户消息、引用、图片 | 当前用户消息、引用、图片 |

连续两轮的目标布局：

~~~text
第 N 轮：  固定 System → 基础上下文 → 既有历史 → N 轮动态资料 → N 轮用户消息
第 N+1 轮：上述实际输入的完整前缀 → N 轮最终回复 → N+1 轮动态资料 → N+1 轮用户消息
~~~

情绪和时间不会写入私聊固定 System；每轮仍读取实时状态和检索结果，记忆顺序保留检索相关性。当前用户始终是初始请求的最后一条消息，兼容图片装载。旧数据库历史继续保留原参考语义；检查点中的 Assistant／Tool 消息保持真实角色，历史工具不会重新执行。群聊保持原来的无历史请求结构，不创建跨轮检查点。其他任务的模型输入保持不变。

固定解释策略在可修改的 `Prompts/ChatContext.prompt` 中，通过 `{{identity}}`、`{{toolsAvailable}}` 两个占位符装配；Shared 仍为公共规则。与其他 Prompt 一样，修改文件后重启生效；新的完整 System 参与兼容性指纹，使旧检查点自动失效。历史情绪、时间和工具结果只代表当时状态；历史回复、摘要、记忆、笔记和动态资料不能授予权限或指示新工具执行。当前时间、动作和记忆写入仍走现有工具与授权流程。

### 检查点与来源

`ConversationReplays` 每个逻辑 Conversation 最多一条最新快照，绑定 Bot、用户范围、格式和状态版本、截止轮次、最终回复 ID、固定 System／模型协议／工具／Tokenizer／预算指纹及摘要基线。普通 session 切换可继续使用；较早任务不能读入未来检查点。截止轮次后存在尚未纳入的有效消息时，回退数据库历史，避免遗漏或重复。

快照采用带版本的显式 DTO，保存角色、有序内容块、原文本和引用包装、工具调用 ID／名称／原始参数字符串／结果及所需思考协议字段；通过官方 SDK 适配层还原。未知或无法无损编码的内容会放弃检查点。图片只保存资源 ID、媒体类型和内容指纹，每次发送前重新验证文件，缺失或变化时重建；不额外保存 Base64。思考字段不进入最终用户消息或普通日志。

普通聊天在图片装载及最终预算检查后观察实际输入；工具聊天在每次 ToolContextBudget.Prepare 和最终检查后观察。保存的是最后一次实际输入加最终回复，包括实际保留下来的工具链；来源集合保守覆盖所有已消费资料。历史按完整轮次裁剪后，从实际发送内容建立新检查点，不再宣称完整复用上一轮前缀。

回复、来源快照、检查点和任务完成在同一事务提交。失败、输出截断、取消、失租约、尚未完成的工具调用或 interaction_no_reply 不发布完整回复检查点。状态版本、截止轮次与 Conversation 提交锁阻止旧任务覆盖新状态；冲突时跳过检查点写入。

`ReplayDependencies` 按资源种类、ID、版本索引递归来源和笔记／媒体依赖。每次发送前沿用 ContentSources、NoteSources 及用户授权校验，递归深度 16、来源数量 512 等限制不放宽。有效期不超过已保存原文、媒体及摘要安全投影的到期时间。

以下情况重建：来源撤回、修改、失效、过期或隐私删除；记忆／关系／笔记来源变化；授权或用户范围变化；摘要版本、投影或覆盖边界变化；身份、固定 Prompt、模型协议、工具、Tokenizer 或预算配置变化；媒体不可恢复或格式损坏。正常情绪变化和时间推进仅追加到末尾。撤销、笔记删除、隐私清理和到期清理会物理删除受影响快照正文及依赖；关闭开关后清理仍继续运行。

### 开关、部署与观察

`Chat:ContextReplayEnabled` 默认 true。关闭后停止读取和写入检查点，保留新的私聊布局、来源校验和容量摘要策略。旧数据不回填，首次成功聊天自然建立检查点。

部署先应用 `20261028103350_ConversationReplay` 增量迁移，再部署应用。迁移在现有 InitialCreate 基线上增加两张表，不要求重建已采用该基线的数据库。

Chat 结构化日志记录检查点命中／重建原因、重放轮次数、历史裁剪数量、完整候选及实际输入 Token 估算和摘要压力原因。供应商提供缓存输入 Token 时记录缓存量；同时提供总输入时可计算非缓存输入，缺失值为 unknown。计费流程不变，不用本地前缀一致性推算供应商命中率。

验收分两层：假模型捕获 HTTP 的有序 messages，并单独比较工具定义，确定满足条件时下一轮保持输入前缀；生产运行另行观察供应商缓存 Token、输入成本与延迟，不承诺固定提升比例。

## 后台任务

### RollingSummary

Chat 只在摘要覆盖边界之后、最近 6 轮之外存在有效完整旧轮次时调度摘要，并满足任一容量条件：有效数据库历史达到 38 条；完整候选 Context（包含工具定义，在可选资料裁剪前）达到可用输入预算的 80%；本轮发生历史裁剪（含工具阶段裁剪）。可用预算为 InputLimit 扣除本轮实际预留的工具空间。38 条给 40 条读取上限预留一轮普通问答空间。

同一 Conversation 已有 Pending 或 Running 摘要时不重复排队；未配置 RollingSummary 或没有可压缩轮次时不创建任务，继续依靠有限历史及裁剪。普通 session 切换不会单独触发摘要；失败不推进边界，实际发布新摘要后才重建基线。摘要提示词、模型、分片、压缩、来源验证和断点逻辑不变：从前一份摘要后按顺序读取，每页 80 条只是批量；通常保留最新 6 轮原文。

每次用完整 Prompt 检查预算；一条长消息也能按字符偏移分片，保留来源和时间。成功后把草稿、游标和来源指纹写入 `Outbox.ProgressJson`，重新排队继续。完整一轮处理完才推进公开摘要的边界；重启后从检查点继续。来源撤回、修改或设置变化会使旧草稿失效。

模型输出截断时最多缩小输入重试两次；生成的摘要超过 600 字符或目标 Token 数时再压缩一次。指令、旧摘要与必要元数据本身已超限，或压缩仍失败时，任务会明确失败，保留可诊断的错误。

### Reflection / Emotion / Relationship / Memory

FullReflection 从最早未处理消息开始读取，每页 100 条，持续推进到任务边界。长消息分片；LightReflection 与 StrongReflection 分别使用自己的模型预算。较小的 Strong 模型会再次拆分待复核片段。

分批结果和来源记录在任务检查点中。所有批次完成后才写入一份 ReflectionResult，创建 Emotion、Relationship、Memory 三类后续任务，避免每处理一个片段就重复触发情绪更新。情绪提案按批次合并，事实和关系提案合并证据来源；分片分析不等价于模型一次看到无限完整对话。

### 记忆维护

优先一次判断候选与相关事实；装不下时，按相关事实及其完整证据分组判断，保存中间决策。分组结束后才提交修改。缺失证据、单组必要证据超限或多组决策无法一致合并时，候选标为 Deferred，已有事实保留。

### 生成结果校验

所有生成任务都经过 ModelRouter 的统一最终预算检查与输出截断检查。固定输入任务不会绕过限制，也不会把 `finish_reason=length` 的不完整输出当作成功结果保存。分批不是对任意 Prompt 自动裁剪：只有理解业务边界的摘要、Reflection 和记忆维护流程负责拆分。

### Embedding

Embedding 的 ContextWindow 表示单次输入上限，无输出预留，同样扣除 512 Token 余量。超长检索问题分块嵌入、分别检索后融合排名。需要持久化的单条事实过长时拒绝或暂缓，避免截断事实却仍将其当作完整证据。

## 配额、失败和诊断

上下文限制、输出截断、日/月配额、传输失败分别处理。后台任务耗尽配额时排到下一 UTC 配额周期，保存已有进度，不消耗失败重试次数；聊天返回额度提示。单次请求本身超过总配额则无法靠等待解决。

控制台模型列表显示实际使用的词表，用量列表显示估算请求数。日志记录任务、模型、词表、输入、输出预留和剩余预算，不记录 Prompt 正文。供应商返回 usage 时采用其数值；未返回时估算。请求发出后结果丢失等不确定失败按预留上限估算结算，可能高于实际费用，不能视为供应商账单。

未匹配词表时仍使用估算；图片与协议开销也存在估算。512 Token 余量不能代替正确配置模型窗口，供应商的实际计数仍可能不同。

## 额度预留与进度存储

Bot 的日 / 月额度按 UTC 统计，不按任务分别分配。TokenBudget 以短串行化事务检查已结算用量和有效预留，再写入 Usage；网络调用不持有该事务。调用完成后结算供应商用量或估算值，预留 15 分钟后失效，失效超过一天的预留由清理任务删除。跨日仍有效的预留计入当前额度。

模型配置错误和供应商要求延迟的请求释放预留，其他不确定失败按估算结算。`Usage.Estimated` 标记当前结算是否包含估算；未带该标记的历史记录不能据此认定为供应商精确计量。

摘要、反思和记忆维护的分批状态保存在 `Outbox.ProgressJson`，任务完成后清空。没有检查点的任务从头执行。部署与数据库恢复见 [运行指南](operations.md)。
