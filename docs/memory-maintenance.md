# Bot 自主维护记忆

人定义开放边界，Bot 在边界内自主整理记忆。自动学习和维护需本人开启长期记忆，不会自行开启授权或扩大私人范围。

独立归档自动执行并受用户开关控制，不增加逐条审批。仅私人来源参与维护；Notes 使用独立授权和版本来源，不能作为正式事实证据。明确依赖失效 Memory 的 Notes 会隔离，独立 Notes 的彻底删除通过本人专用入口执行。

## 用户边界

个人空间的“记忆偏好”提供四个自动维护开关，也可通过 GET / PUT `/api/v1/me/memory-settings` 读取和设置：

| 字段 | 默认 | 服务端行为 |
| --- | --- | --- |
| `allowMemoryMerge` | true | 合并同义事实，追加去重后的证据和最近确认时间 |
| `allowMemoryUpdate` | true | 补充或更新事实；创建新版并归档旧版 |
| `allowMemoryArchive` | true | 在没有替代事实时，单独归档已明确失效的事实 |
| `retainMemoryHistory` | true | 保留归档正文，供本人查看；关闭时清除已有和后续归档正文及关联维护记录中的内容 |

长期记忆自身默认关闭。这四项不会改变 `allowMemory` 或 BotId + SubjectId 的私人范围。更新旧版所需的归档属于 `allowMemoryUpdate`；单独撤销事实的归档由 `allowMemoryArchive` 控制。省略可选设置字段会保留原值。

归档历史不进入普通聊天检索。本人列表默认只显示当前版本；`GET /api/v1/me/memories?includeArchived=true` 可以查看保留的历史。控制台同时展示归档版本。关闭历史保留属于对记忆库中归档内容的自动遗忘，不清除原始聊天记录；原始聊天仍遵循既有保留期。此版本没有按天数自动清理当前事实的定时遗忘规则。

## 维护流程

1. 反思提案经校验后，只有明确、非敏感且有本人消息证据的合格候选进入 `MemoryCandidates`，不会直接参与聊天检索；同一反思里的完全重复候选只排一个任务。反思触发和模型路由见 [Reflection 与 Memory](reflection-memory.md)。
2. 完全相同的正文走快速合并路径；`FactKey` 相同作为查找相关事实的线索。
3. 其他候选先生成向量，使用当前 Embedding Profile，在同一 Bot / SubjectId 的非撤销、未归档私人记忆中精确召回 Top 10，并加入同 FactKey 的记忆。其他 Bot 或用户的事实不参与合并。
4. 相关事实及原始消息证据交给 `StrongReflection` 路由，返回 Add / Merge / Supplement / Update / Archive / Defer。相似度只用于找候选，没有“超过阈值即合并”的规则。模型必须区分人物、否定、数字和时间关系。
5. 服务端校验操作、目标、用户开关、来源和证据。过旧的证据不能替换、补充或归档较新的事实；不确定或不允许的操作暂缓处理。Defer 不形成正式记忆，新消息可以提供后续依据。
6. 外部模型调用结束后才开启提交事务；按用户 Epoch 加锁，并重新核对整个作用域的记忆 ID / Revision / Status。并发新增或修改会触发重试和重新判定，防止两个任务都把同一事实视为新事实。

“住杭州”与“目前住在杭州”可以合并；“上个月已搬到上海”可以生成当前版本并归档杭州版本；无法判断时间的“住上海”可以暂缓。以上是期待的模型判定，实际语义准确性取决于所配置的模型，不是只由向量分数保证。

新增和更新直接复用候选向量。补充后的完整正文如果发生变化，需要为新正文再生成一次向量。完全重复的快速合并不调用模型。原始事实无相关候选时可直接准入，无需一次额外的生成请求。

## 更新与删除

更新保留 `SupersedesMemoryId` 版本链和 `ArchivedAt`；合并保留原正文，追加独立证据、`LastConfirmedAt` 并提升 `Revision`。新事实的确认时间来自证据消息时间，不以任务完成时间代替。

归档旧版时删除对应向量，并停用依赖旧版的助手上下文、摘要、Notes 判断和待发送回复。

管理已有记忆不受自动学习和自动维护开关限制。人工 Edit 使用期望 Revision 和持久幂等键创建当前新版，不借用隐私删除；新正文立即有效，Embedding 异步。独立 Archive 不标记 IsOutdated。两者只调整已记录依赖的资格，不改原消息、媒体、Summary.Text 或独立 Notes/关系正文。

Forget 处理精确版本族、所有 Profile 向量及确切候选/Reflection Memory 子项，并建立旧证据抑制；不清同一用户的全部派生数据。Erase 另需限时预览与完整本人私聊消息确认，按冻结清单清理和逐项核验。后续合法当前证据可以自动再学，不以 FactKey hash 构造永久语义黑名单。完整数据模型及并发边界见 [Memory 生命周期](memory-lifecycle.md)。

更改边界会提升 Epoch，并取消旧的待处理候选。已经完成的正常维护记录可由本人通过 `GET /api/v1/me/memory-maintenance?skip=0` 查看，按创建时间倒序分页，每页最多 100 条；Bot Owner 身份不能读取其他人的记录。

## 模型与故障处理

配置独立 Embedding 路由和 StrongReflection 路由。缺少相关记忆的新 Profile 向量时，每次最多补排 50 个 Embedding 任务，维护任务等待 30 秒后重新检查；不能将“暂时缺少向量”当作“没有相关事实”。Profile 按 Bot、接口、模型、维度和版本隔离。

供应商错误或无效结构化响应不会改写正式记忆，候选保持隔离。配置错误、无法容纳的必要上下文和输出截断可能进入 DeadLetter；后台周期额度耗尽则延后到下一 UTC 周期。修复和重试见 [运行指南](operations.md#任务失败与重试)。当前使用 pgvector 精确查询，没有近似索引或相似度阈值配置。

自动化测试覆盖模拟模型的维护决策、权限和并发变化，并在随机临时 PostgreSQL 数据库中验证迁移、真实 pgvector 召回、更新和版本链删除。模型供应商的实际语义质量还需用真实中文样本评估。

测试运行方式和真实供应商验收边界见 [测试指南](../tests/README.md)。
